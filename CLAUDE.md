### WfFormat 1.6 fields used

`workflow.specification.tasks[]`: `id`, `parents`, `children`, `inputFiles`, `outputFiles`. `workflow.specification.files[]`: `id`, `sizeInBytes`. `workflow.execution.tasks[]`: `id`, `runtimeInSeconds`.

### Units (a classic 8x bug)

File sizes are **bytes**. Link capacity is **Gbps = 10^9 bits/s**, so bytes/s = `gbps * 1e9 / 8`. GB means 10^9 bytes. The sanity test in section 9 catches unit mistakes.

### Determinism pitfalls

- Never use Python's built-in `hash()` for anything that affects results; string hashes change between processes. Use `hashlib.sha256`.
- Never let the iteration order of a `set` affect results; sort first. Dicts keep insertion order, so build them in a fixed order.
- One seeded RNG per run (`random.Random(seed)` or `numpy.random.default_rng(seed)`), and pre-generate random series at the start so the order of later calls can't change them.
- Never read the wall clock inside simulation or planning logic.

## 8. Part 1 — extraction (reference implementation, tested)

- **Sites:** compute sites `["Caltech", "UCSD", "FNAL", "ORNL"]`. Raw inputs start at source site `"CERN"`. `"StarLight"` is a transit-only node (no tasks).
- **Placement:** a seeded sha256 hash, so it is repeatable and varies with the seed.
- **Deadlines (critical-path method):** workflow deadline **D** = `slack` × (critical path if data moved instantly). A transfer's deadline is the latest start time of the earliest task at the destination that needs the file. `slack` is fixed at **1.5**; don't tune it.
- **Copies:** one transfer per (file, destination site).

```python
"""Part 1: turn a WfInstances (WfFormat 1.6) JSON file into a list of network transfers."""
import hashlib
import json
from graphlib import TopologicalSorter


def load_instance(path):
    with open(path) as fh:
        d = json.load(fh)
    spec = d["workflow"]["specification"]
    exe = d["workflow"]["execution"]
    tasks = {t["id"]: t for t in spec["tasks"]}
    size = {f["id"]: f["sizeInBytes"] for f in spec["files"]}
    runtime = {t["id"]: t["runtimeInSeconds"] for t in exe["tasks"]}
    return d["name"], tasks, size, runtime


def place_tasks(tasks, sites, seed=0):
    """Give every task a site. Same seed -> same placement, so runs are repeatable.
    Uses sha256, not Python's hash(), because hash() of a string changes between processes."""
    def pick(tid):
        h = int(hashlib.sha256(f"{seed}:{tid}".encode()).hexdigest(), 16)
        return sites[h % len(sites)]
    return {tid: pick(tid) for tid in tasks}


def latest_start_times(tasks, runtime, slack):
    """Critical-path method: the latest each task can start without the workflow missing its deadline."""
    order = list(TopologicalSorter({tid: t["parents"] for tid, t in tasks.items()}).static_order())
    finish = {}
    for tid in order:  # forward pass: earliest finish if data moved instantly
        finish[tid] = max((finish[p] for p in tasks[tid]["parents"]), default=0) + runtime[tid]
    deadline = slack * max(finish.values())
    latest_finish = {}
    for tid in reversed(order):  # backward pass
        latest_finish[tid] = min((latest_finish[c] - runtime[c] for c in tasks[tid]["children"]), default=deadline)
    return {tid: latest_finish[tid] - runtime[tid] for tid in order}, deadline


def extract_transfers(path, sites, source_site, slack=1.5, seed=0):
    name, tasks, size, runtime = load_instance(path)
    place = place_tasks(tasks, sites, seed)
    producer = {f: tid for tid, t in tasks.items() for f in t["outputFiles"]}
    latest_start, deadline = latest_start_times(tasks, runtime, slack)
    transfers = {}
    for tid, t in tasks.items():
        for f in t["inputFiles"]:
            src = place[producer[f]] if f in producer else source_site
            dst = place[tid]
            if src == dst:
                continue  # same site: no network transfer needed
            key = (f, dst)  # one copy per destination site, even if several tasks there need it
            need_by = latest_start[tid]
            if key not in transfers or need_by < transfers[key]["deadline_s"]:
                transfers[key] = {
                    "id": f"{f}@{dst}", "file": f, "bytes": size[f],
                    "src": src, "dst": dst,
                    "after_task": producer.get(f),  # None = raw input, ready at t=0
                    "deadline_s": need_by,
                }
    out = list(transfers.values())
    for tr in out:
        tr["deadline_s"] = round(tr["deadline_s"], 3)
    return {"workflow": name, "deadline_s": round(deadline, 3), "transfers": out}
```


### Scenarios (`configs/scenarios.yaml`). All times are **fractions of the workflow deadline D**, so the same scenario stresses short and long workflows alike

```yaml
background: {mean: 0.2, wave: 0.1, period_frac: 0.5, noise: 0.05, interval_frac: 0.005}
normal: {events: []}
congestion:
  events:

```

A rough throwaway prototype of this spec (baseline only, tuning seeds; your simulator will differ somewhat) found:

- **1000Genome 8ch at data_scale 100:** both events stress the baseline. Mean completion was about 1.19 D under congestion and 1.71 D under link failure, versus 0.99 D in normal.
- **Montage 0.1° at data_scale 200:** the link failure stresses it (about 1.03 D vs. 0.78 D). Congestion on **any** single link barely matters, because at that scale Montage is compute-bound.

Stage 4 handles both cases (section 14).

### Simulator semantics

- **Time step:** `dt = D / 1000` (or an exact event-driven design, if you prefer; see section 2). Max time = `20 * D`.
- **Background load** on link `l` at time `t` = `mean + wave * sin(2*pi*t / (period_frac*D) + phase_l) + noise_l[k]`, plus `extra_load` during an active surge, clipped to [0, 0.95].
  - `phase_l` is drawn from the run's RNG.
  - `noise_l[k] ~ Normal(0, noise)` is piecewise constant over intervals of length `interval_frac * D` and pre-generated at the start.
- **Free capacity** = `gbps * (1 - background)` in bits/s, converted to bytes/s, or 0 while the link is down.
- **Ready transfers:** the producer task has finished (or `after_task` is None) and the plan's `start_s` has passed.
- **Sharing:** transfers whose path has a down link are stalled and take no share. On each link, moving transfers split free capacity in proportion to priority weight (priority 2 → 2, priority 1 → 1). A transfer's rate is its smallest share along its path.
- **Arrival:** when remaining bytes reach 0, the file arrives after the path's total one-way delay.
- **Stalls and failures:** a stalled transfer accumulates stall time. At `timeout = 0.1 * D`, the attempt **fails**:
  - `failed_attempts += 1`, and the transfer is added to the failed set
  - remaining bytes reset to the full size, and the stall timer resets
  - the planner receives a `transfer_failed` event
  - the transfer stays queued on its (possibly updated) path
- **Events to planners:** at each event start/end, call `planner.on_event(event, view)` with `{"type": "link_down"|"link_up"|"surge_start"|"surge_end"|"transfer_failed", "t": t, "link": [a, b] or "transfer_id": ..., "seq": n}`. Validate any changes before applying them.
- **Tasks:** a task starts when all its parents have finished **and** all its input files are at its site. It runs for its real `runtimeInSeconds` (not scaled). Its outputs appear at its site when it finishes. Compute capacity is unlimited (state this as a limitation).
- **End:** when every task is done, or at max time (`completed=False`, `completion_s=NaN`).
- **`snapshot()`** returns an independent copy of the current state for `simulate_plan`. It must not touch the real run's RNG or state.
- **Views:** planners receive a read-only view that exposes only the present: current free capacities, link up/down, transfers' status, and the clock. They never see the future.

### Metrics per run

- `completed`, `completion_s`
- `failed_attempts` and `failed_transfers` (distinct transfers with at least one failed attempt)
- `late`: transfers arriving after `deadline_s`; transfers that never arrive count as late
- `n_transfers`, `gb_moved` (arrived bytes / 1e9), `avg_gbps` (arrived bits / completion time / 1e9)
- `data_wait_s`: sum over tasks of (start time − time its last parent finished, or 0 if it has no parents)
- `reroutes`: path changes after the initial plan
- `decisions`: number of logged decisions

### Required tests

- **Units sanity:** one 10 GB transfer on a single empty 100 Gbps link with no background and `dt = 0.01` arrives at 0.8 s + delay (± dt).
- **Failure path:** a transfer whose only path goes down stalls, fails at the timeout, and counts once in `failed_transfers` even if it fails twice.
- **Determinism:** the same small run gives identical metrics in two separate subprocesses with different `PYTHONHASHSEED` values.

## 10. Planner interface and validation

```python
class Planner:
    name: str          # "baseline", "baseline_reroute", "agents"
    mode: str          # "rule" (default) or "llm"
    def plan(self, transfers: list[dict], view) -> dict:
        """Return {transfer_id: {"path": [sites...], "priority": 1 or 2, "start_s": float}}."""
    def on_event(self, event: dict, view) -> dict:
        """Return changed entries in the same shape, or {}."""
```

**Validation** (in the simulator and in the `submit_plan` tool):

- the transfer id exists
- the path is simple, starts at `src`, ends at `dst`, and uses only existing links
- priority is 1 or 2, and `start_s >= now`

Invalid entries are rejected, logged, and the previous plan entry stays.

## 11. Baselines

- **`baseline`** (the one Risshab promised): lowest-delay path (`networkx.shortest_path(G, src, dst, weight="ms")`), all priority 1, start as soon as ready. `on_event` returns `{}`, so stuck transfers wait and may time out.
- **`baseline_reroute`** (an ablation, which is Risshab's answer to "isn't this just rerouting?"): same as `baseline`, but on `link_down` or `transfer_failed` it moves each unfinished transfer whose path uses a down link to the lowest-delay path that avoids currently-down links. It ignores surges and never uses priorities.

The prototype found two things worth knowing in advance:
- Simple rerouting recovers most of the outage damage on 1000Genome.
- When every transfer reroutes onto the same backup path, it can make things *worse*, which the prototype saw on Montage with large data.

Congestion is where coordination should matter most. Treat these as hypotheses to test, not claims.

### Tools (`att/tools.py`): plain functions over a twin view; they reveal only the present

|---|---|---|

### MCP server (`att/mcp_server.py`)

- `build_server(twin_or_view) -> MCPServer` registers one `@mcp.tool()` wrapper per tool.
- A module-level `mcp` server built on a cheap demo twin (1000Genome 2ch, normal) plus `if __name__ == "__main__": mcp.run()`, so the Inspector and the stdio demo work.

### Tool client (`att/tool_client.py`)

Record every tool call (name, args, short result summary) into the current decision log entry.

### Agents (rule mode: the default and what the main results use)

- **Workflow agent** (SciNet 2.2.1):
  - For each transfer, earliest possible arrival = producer's earliest finish + `estimate_transfer_time` on the lowest-delay path.
  - `slack = deadline_s - earliest arrival`.
  - The lowest-slack 30% of transfers get priority 2 (the fraction is a tunable agent parameter).
  - Output: a ranked list, each with a one-line reason.
- **Network agent** (SciNet 2.2.2, 2.2.3):
  - For each transfer, call `get_paths(k=3)` and `estimate_transfer_time` for each path.
  - Recommend the fastest path with no down link.
  - Flag busy links (free capacity below 30% of capacity).
- **Coordinator** (SciNet 2.2.6), the agent team's `Planner`:
  - **Initial plan:** process transfers by (priority desc, slack asc). Among each transfer's top-3 paths, choose the one with the lowest projected bottleneck load (bytes already assigned to the link plus this transfer, divided by the link's free bytes/s).
  - **Pick a draft:** run `simulate_plan` on this draft and on the plain network-agent draft, and keep the better one (completion time, then late, then failed).
  - **Submit:** call `submit_plan`.
  - **On `link_down` or `transfer_failed`:** reroute only the affected unfinished transfers, spreading them across alternatives by projected load. Don't pile everything onto one backup path.
  - **On `surge_start`:** move transfers off the surged link when another path is estimated faster, priority 2 first.
  - **On `link_up` / `surge_end`:** move not-yet-started transfers back if that's faster.

You may design a better strategy (section 2). Keep it explainable, and tune it only on dev workflows with tuning seeds.

### Optional LLM mode

Only after the definition of done is met, and only if Risshab provides a key and says yes:

- The coordinator sends both agents' proposals to an LLM with MCP tool access.
- It asks for a JSON plan plus a short reason, validates it, and falls back to rule mode if invalid.
- Temperature 0; at most one call per plan and one per event.
- Results are reported separately and labeled `mode=llm`.

## 13. Part 4 — decision log, manifests, replay

**Decision log** (`att/decision_log.py`): one JSON object per line in `results/logs/<run_id>.jsonl.gz`. Log every planner, the baselines included.

```json
{"run_id": "1000genome-8ch__link_failure__seed3__agents", "seq": 7, "t": 90.3, "agent": "coordinator",
 "trigger": {"type": "link_down", "link": ["StarLight", "Caltech"], "seq": 2},
 "saw": {"stuck_transfers": 6, "busy_links": [["StarLight", "FNAL"]]},
 "tool_calls": [{"tool": "get_paths", "args": {"src": "StarLight", "dst": "Caltech", "k": 3}, "result": "3 paths"}],
 "decision": {"<transfer_id>": {"path": ["CERN", "StarLight", "FNAL", "UCSD", "Caltech"], "priority": 2, "start_s": 90.3}},
 "reason": "Direct link down; spread 6 stuck transfers over the two remaining routes by projected load."}
```

**Manifest** (`results/manifests/<run_id>.json`): workflow file, scenario, seed, planner name and mode, every setting, the git commit hash, package versions, and the run's metrics.

**Replay:**

- `att/replay.py` has a `ReplayPlanner` that returns the logged initial plan, then the logged updates in order at each `on_event` call. It runs no agent code and makes no LLM calls.
- It checks that each incoming event matches the logged trigger (type, seq, t), and raises a clear error if not.
- `scripts/replay.py --run <id>` or `--all` re-runs and compares against the manifest: integers exactly, floats within 1e-9 relative. It prints `REPLAY OK <run_id>` or the differing fields, and exits non-zero on any mismatch.
- A pytest replays one baseline run and one agents run on a dev workflow.

## 14. Tuning (Stage 4) and experiments (Stage 7)

**Tuning** (`scripts/tune.py`; baseline only; tuning seeds 100–104; before agents exist):

1. For **each** workflow (dev and result), pick `data_scale` from `[10, 20, 50, 100, 200, 300, 500, 1000]`: the **largest** value where, in `normal`, the baseline's mean completion is at most D and mean `late` is at most 1% of transfers. The prototype landed on about 100 for 1000Genome 8ch and about 200 for Montage 0.1°; let the rule decide for your simulator.
2. Check that `congestion` and `link_failure` each stress the baseline: mean completion at least 10% worse than `normal`, or mean `late + failed_transfers` > 0. If a scenario doesn't stress a workflow, try these in order and log each attempt:
   - (a) move its event to the link that carries the most baseline bytes during the event window in `normal`
   - (b) raise `extra_load` (for a surge) so the link reaches the 0.95 load cap
   - (c) if it still has no effect, **keep the scenario as is and report it as a finding** (for example, "Montage is compute-bound at this scale, so congestion barely matters")

   Never raise `data_scale` above step 1's value or invent harsher conditions just to manufacture a difference.
3. Freeze the values in `configs/experiment.yaml`. Record the full tuning table in `docs/BUILD_LOG.md`.

**Experiments** (`scripts/run_experiments.py`):

- 2 result workflows × 3 scenarios × 10 evaluation seeds (0–9) × 3 planners (`baseline`, `baseline_reroute`, `agents`) = **180 runs**.
- One row per run in `results/summary.csv`: `workflow, scenario, seed, planner, mode, completed, completion_s, failed_attempts, failed_transfers, late, n_transfers, gb_moved, avg_gbps, data_wait_s, reroutes, decisions`.
- Runs must not depend on each other. Running a subset gives the same rows.

## 20. Troubleshooting

- **`ImportError` for `FastMCP` or odd MCP errors:** you're using the v1 API; see section 5.
- **Results differ between runs:** look for `set` iteration, built-in `hash()`, unseeded randomness, wall-clock use, or state shared between runs.
- **Transfers 8× too fast or slow:** bytes vs. bits; run the units sanity test.
- **A scenario changes nothing:** its event doesn't overlap real traffic; apply the Stage 4 rule.
- **Runs too slow:** profile first; then batch tool calls, cache paths per (src, dst), or move to an event-driven simulator.
- **Replay mismatch:** check that every decision (initial plan and every event response) was logged, in order, with the event `seq`, and that rejected entries are handled the same way in replay.
